## Context

A consumer-brand operations team needed a single pane of glass across Amazon, Flipkart, Blinkit, Zepto, and several other marketplaces — each with its own credentials, schema, refresh cadence, and product taxonomy. The team also needed a self-serve report builder so analysts could compose new metrics without engineering involvement.

## My role

I led the analytics ingestion and report-builder modules and contributed across the broader platform. That covered the BullMQ worker design, the CASL RBAC layer, the D3.js report-builder surface, and the 192+ NestJS REST endpoints powering the dashboard.

## Architecture

- NestJS monolith with feature modules per channel plus a shared analytics module.
- BullMQ + Redis for async sync jobs (one queue per channel, separate concurrency knobs).
- PostgreSQL as primary store; per-channel staging tables flow into consolidated analytics tables.
- Next.js 15 dashboard with React Server Components for the static shell and client components for the interactive D3/Chart.js widgets.
- Socket.io for real-time refresh of "currently syncing" widgets; CASL for permission checks; TOTP via `otplib` for 2FA.

## Key technical decisions

- **Why BullMQ for ingestion queues** — durable, Redis-backed, with first-class delayed/retry/repeat semantics; it aligns with the Node ecosystem we already operate and avoids the operational overhead of a separate message broker.
- **Why CASL for RBAC over a roles table** — analytics access decisions are condition-rich (a user can read reports they authored or reports their team owns); CASL's ability-based model expresses this cleanly while a flat roles table would hard-code one permission shape.
- **Why D3 for the report builder, not a chart library** — the report builder requires user-defined dimensions, measures, and interactions that Chart.js or Recharts don't support without fighting their abstractions; D3 takes longer per chart but doesn't cap the design.

## Constraints

With 192+ endpoints the ingestion contract is the slow-changing part of the system, which makes backward compatibility on queue message shapes critical. Aggressive Redis caching accelerates dashboards but can silently serve stale cohort slices if cache invalidation is imprecise.

## What I'd do differently

I'd materialize cohort-rollup tables on a schedule rather than recomputing per request, and introduce read replicas before vertically scaling the primary — the analytics query patterns are read-heavy and well suited to horizontal read scaling.
